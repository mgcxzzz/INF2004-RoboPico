# RoboPico Buddy 1–5 RTOS v0.2.13

This integration candidate builds on Buddy 1–4 v0.2.12 and the Buddy 5 review
branch. The combined image still needs a physical obstacle run. Use the UF2
and dashboard from the same bundle.

## Set up

1. Extract the bundle and close the old dashboard launcher. With the robot
   stopped, hold BOOTSEL while connecting the Pico W by USB. Copy
   `firmware/robopico_buddy1_5_rtos_v0_2_13.uf2` to `RPI-RP2`.
2. Start the bundled dashboard. On Windows run **Start dashboard.cmd**.
   On macOS run `python3 tools/dashboard/run_dashboard.py` from the extracted
   folder. This uses Python 3.10+ and Mosquitto. If your Wi-Fi or laptop broker
   address changed, use **Configure WiFi.cmd** or run
   `python3 tools/rtos_migration/provision_network.py` on macOS. Follow the BOOTSEL
   prompt to update the saved network settings.
3. Power the car with its usual powerbank and motor supply. Place it flat and
   still for IMU calibration. Connect the browser dashboard at
   `http://localhost:8765` to `ws://localhost:9001`. Confirm car online, firmware
   **Buddy 1–5 v0.2.13**, Telemetry on, and **Baseline · 45 mm/s**. Apply and
   read back your barcode mapping. Dashboard Start uses a two-second countdown.
   USB serial and the capture helpers are optional.

## First hardware checks

1. Start on a clear straight, with the sonar and servo fitted in the tested
   configuration. Check that Start works, line following continues past the
   first few seconds, and Pause, Resume and Stop work while tracking. If Start
   is rejected, capture the command response and the Obstacle & avoidance card.
2. Place the known demo obstacle on a straight with at least 200 mm of steady
   line following before the sonar first reaches 300 mm. Leave room on both
   sides for the probe, bypass and return to the line. Look for detection,
   the width policy and displayed estimate, the chosen bypass side, then line
   reacquisition and resumed tracking. The width card distinguishes an
   estimated width from the 150 mm assumption.
3. With space to stop, check a close obstacle on a bend. The car should hold
   with `NOT_STRAIGHT` once it confirms the close obstacle with the straight
   gate closed. Press Stop to clear the hold. During an active avoidance,
   dashboard Pause ends the run. Use a fresh Start to run again.
4. During separate controlled runs, check that GP20 and the IMU pickup stop
   each cut drive during Buddy 5 motion. Use an unobstructed approach and
   stay outside the sonar field while observing the maneuver.

## Save evidence

After each failure or the first complete obstacle bypass, press **Stop** and
keep the car and broker powered. Wait about five seconds for coordinator Off,
then click **Download run ZIP**. Export before Reset, reboot or the next Start.
Send that ZIP and identify the obstacle placement, approximate run time of the
event, and last stage reached. If collection produces a `_PARTIAL.zip`, keep
it and retry while the same stopped car is still online. A short video of the
first approach through line reacquisition helps correlate motion with the logs.

## Integration notes

Buddy 5 submits finite movement requests through the shared navigation and
motion executor. Its signed adapter uses the existing continuous wheel
controller and commits through the same generation and safety checks as the
other motion owners. The µT-Kernel worker services sonar, servo and telemetry
at lower priority than the motion task. Buddy 3 resumes only after the
coordinator accepts hand-back. The SDK width, direction and bypass modules
retain their reviewed implementations under coding exception CEX-08.

The review run stopped at 295 mm with `NOT_STRAIGHT/BEND_ENTRY`. This build
allows pre-candidate steering corrections within the 6° encoder heading
budget over 200 mm. It still blocks a sustained bend candidate, confirmed
bend, bend exit, junction, recovery, or stale line sample. Detection still
requires three fresh close echoes. Host simulations exercise this change,
ownership, and stop behavior. Physical sensor timing, width accuracy and
reacquisition on the demo track remain to be confirmed.

## Rebuild and check

On the project's Windows build host, run `tools/rtos_migration/build_release.sh
APP=rtos_buddy1_5` in Git Bash using the pinned adjacent `.buddy2-tools` SDK
and Arm toolchain. The host tests run through
`python tools/rtos_migration/run_tests.py`. Run
`node --test dashboard/test/test_b5_rtos.js` for the Buddy 5 wire vectors.

The integration checks passed 55 C programs and nine Python test stages.
All 36 obstacle simulations also passed with undefined-behavior traps enabled.
The dashboard browser check used simulated MQTT and verified full and partial
run ZIPs. Building `APP=rtos_buddy1_4` from the combined source reproduced the
published v0.2.12 UF2 byte for byte. The combined image has 1,016 bytes of
estimated kernel allocation headroom after boot allocations. Confirm startup
and runtime timing on the Pico W during the first hardware run.
