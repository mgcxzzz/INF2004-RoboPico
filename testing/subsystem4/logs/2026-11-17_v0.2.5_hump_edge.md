## Ramp assistance and reproduced timing defect

Ramp assistance DID activate:7 activations. Activation1 at16:44:08.627Z ends STALE at16:44:09.696Z; six later activations each end STALE, after73/81/34/197/298/178ms. Several end records say sampleValid=true and their interval invalidSamples=0. This STALE is an internal IMU-tilt-age condition, not MQTT heartbeat.

Call chain: control.c captures board_time_us at loop start -> LinePlanner CircuitInput.now -> rl_power -> ri_ramp_step(i->now,...) -> ri_tilt_snapshot obtains possibly newer core0 sample -> ri_ramp_request passes cached now and newer tilt timestamp -> ramp_assist_step compares unsigned64 now-last_sample_us to60ms and200ms. A newer sample underflows age.

One targeted host probe against actual ramp_assist.h confirms: with active valid10mm tilt and next sample1ms newer than cached control time, assisting becomes0/end4(STALE)/sampleValid1. Using time1ms AFTER sample instead leaves assistance active. This proves a reachable firmware race consistent with logged dropouts, not direct per-event proof because exact sampled control/tilt microsecond pairs are not exported.

Production firmware unchanged during analysis. Probe source and native executable are local only. No full regression suite or firmware build was run.
